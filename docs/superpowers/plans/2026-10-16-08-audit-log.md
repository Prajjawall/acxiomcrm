# Audit Log Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans if your harness has them; otherwise execute task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An append-only audit trail written automatically for CRM entity changes and explicitly for security/business events, with an Admin UI to search it.

**Architecture:** `AuditLog` entity + `AuditWriter` (explicit events) + `AuditSaveChangesInterceptor` (automatic old/new capture for `IAuditedEntity` and stamping of `CreatedBy/ModifiedBy`, soft-delete conversion). Immutability enforced in the interceptor and by a SQL trigger. Query side `IAuditQueryService` with filters and paging; MVC UI under `/Audit`.

**Tech Stack:** EF Core `SaveChangesInterceptor`, System.Text.Json, SQL Server trigger, Razor.

**Spec:** PRD AUD-01..06, D-25; DATA-MODEL §3 AuditLogs; SECURITY-AUTHZ §1.

**This plan runs in two parts.**
- **Part A (Tasks 1–4)** runs right after Plan 01 and before Plan 02, because authentication events need `IAuditWriter`.
- **Part B (Tasks 5–6)** runs after Plan 03, because it needs the application shell and design system.

## Global Constraints
- Audit rows are never updated or deleted (code, DB trigger, API surface).
- `OldValue`/`NewValue` hold JSON of **changed properties only**; properties named `PasswordHash`, `SecurityStamp`, `ConcurrencyStamp`, `RowVersion`, `TokenHash` are never captured.
- Timestamps UTC from `IClock`. `IpAddress` ≤ 45 chars. `Details` ≤ 1000 chars (truncate with `…`).
- `AuditResult` is `Success` for committed changes; `Failure` only through explicit `IAuditWriter` calls.
- Interceptor audit rows are written in the **same transaction/SaveChanges** as the data change.

## Review Focus
- A write inside a transaction that later rolls back leaves no audit row for the interceptor path.
- Soft delete: `Remove()` on an `ISoftDeletable` becomes an update flagged `IsDeleted`, audited as `Delete`, never as `Update`.
- Updating only `ModifiedDate/ModifiedBy`/`RowVersion` (no real change) produces no audit row.
- Entities with 10k-character `Notes`... capped at `Limits.Notes` upstream, but audit JSON must still never exceed column limits (nvarchar(max) fine; `Details` truncated).
- Anonymous failed login: `UserId` null, `UserName` null, `Details` has the attempted username.
- Concurrent saves from different users record the right user each time (scoped `ICurrentUser`).
- Attempt to `UPDATE`/`DELETE`/`TRUNCATE` audit rows via raw SQL under the app login fails.

**Files:**

(Module entities come in later plans; this verifies the interceptor in isolation.)
- Test: `tests/AcxiomCrm.Infrastructure.Tests/AuditInterceptorTests.cs`

**Interfaces:**
- Consumes: `IHasTimestamps`, `ISoftDeletable`, `IAuditedEntity` (plan 01), `ICurrentUser`, `IClock`.
- Behaviour: on `SavingChanges(Async)`: for `Added` → stamp `CreatedDate/CreatedBy`, add audit `Create` with `NewValue` JSON of all non-sensitive properties; `Modified` → stamp `ModifiedDate/ModifiedBy`, compute changed properties (ignoring `ModifiedDate/ModifiedBy/RowVersion`), if none → no audit, else `Update` with old/new JSON; `Deleted` on `ISoftDeletable` → convert to `Modified` with `IsDeleted=true, DeletedDate, DeletedBy`, audit `Delete` with `OldValue` snapshot. Audit rows added to the same context before save so they commit atomically. `RecordId` is the entity key; for `Added` entities with store-generated keys, add the audit rows in `SavedChanges` follow-up **within the same transaction** (use `SavingChangesAsync` to begin an explicit transaction if none exists, then a second `SaveChanges` in `SavedChangesAsync` and commit). Specify this two-phase behaviour in the test names.

**Interfaces:**
- Produces:
```csharp
public sealed record AuditFilter(string? UserId, string? Module, string? Action, AuditResult? Result,
    DateOnly? From, DateOnly? To, string? EntityName, string? RecordId, string? Text);
public sealed record AuditListItem(long Id, DateTime CreatedDateUtc, string? UserName, string Module, string Action,
    string EntityName, string? RecordId, AuditResult Result, string? IpAddress, string? Details);
public sealed record AuditDetail(AuditListItem Header, IReadOnlyList<AuditChange> Changes, string? CorrelationId);
public sealed record AuditChange(string Property, string? Old, string? New);
public interface IAuditQueryService {
    Task<PagedResult<AuditListItem>> SearchAsync(AuditFilter filter, PageQuery page, CancellationToken ct = default);
    Task<Result<AuditDetail>> GetAsync(long id, CancellationToken ct = default);
    Task<IReadOnlyList<string>> ListModulesAsync(CancellationToken ct = default);
    Task<PagedResult<AuditListItem>> ForRecordAsync(string entityName, string recordId, PageQuery page, CancellationToken ct = default);   // timeline use, plan 04/07
}
```

Everyone else gets `Forbidden`. `ForRecordAsync` is permitted when the caller can see the record (callers pass only after their own scoped load).
