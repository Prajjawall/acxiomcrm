# Lead Management Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans if your harness has them; otherwise execute task by task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Lead capture, workflow-controlled status changes, assignment, atomic conversion to customer (and optionally an opportunity), search and UI.

**Architecture:** Same module shape as Customers (entity → rules → service → controller/views). `LeadWorkflow` in Domain is the single transition table. Conversion is one service method running in a database transaction and reusing `ICustomerService`'s duplicate detection. The opportunity half of conversion calls an `IOpportunityFactory` seam implemented in plan 06; until then conversion with `CreateOpportunity=true` returns a validation error (explicit, tested).

**Tech Stack:** As plan 04.

**Spec:** PRD LEAD-01..07, AUTHZ-04, D-12, D-13; DATA-MODEL Leads; Source §5.2 workflow table in PRD.

**Depends on:** Plan 04.

## Global Constraints
- Statuses and transition table exactly per PRD §5.2. `Converted` is reachable only via `ConvertAsync`.
- Expected value `0 ≤ v ≤ 100,000,000`, 2 decimals; messages: `Expected value must be between 0 and 10,00,00,000.` (display uses en-IN formatting of the cap).
- At least one of email/phone required: field error on `Email` and `Phone`: `Enter an email address or a phone number.` Both validated if present.
- Lead name required ≤ 150; company ≤ 150; notes ≤ 2000; source and priority from enums; status default `New` on create (creating directly as another status is rejected except `New`).
- Converted and Lost leads are read-only (LEAD-07). Editing them → `Conflict`/validation form error `This lead is <status> and cannot be edited.`. Manager/Admin may reopen Lost → New via `ChangeStatusAsync`.
- Lead codes `LEAD-000001` via `seq_LeadCode`.
- Assignment: Manager/Admin only (`leads.assign`); target active, in assigner's scope; creator-executive owns their own leads.

## Review Focus
- Direct edit POST containing `Status=Converted` (or any status) on the edit form: the edit form **does not** change status. Status moves only through `/Leads/ChangeStatus`; crafted `Status` field on Edit is ignored/rejected.
- Convert a lead whose email matches an existing customer: response offers "link to existing customer" instead of silently creating a duplicate or failing opaquely; confirming links without creating.
- Conversion failure halfway (opportunity validation fails, DB error injected): **nothing** is persisted (no customer, no lead status change, no audit "Converted").
- Converting an unqualified/contacted/new lead → `A lead must be Qualified before conversion.`; converting twice → conflict, no duplicate customer.
- Converted lead where the customer was later soft-deleted: lead detail still renders (link shown as "deactivated customer").
- Expected value `-1`, `100000000.01`, `abc`, 3 decimals `10.005`.
- Lead with only phone / only email / neither.
- Reassign to a deactivated user, or to a user in another team (manager) → rejected.

## Task 3: Lead conversion

**Files:**
- Create: `src/AcxiomCrm.Application/Leads/{ConvertLeadCommand,ConvertLeadResult,IOpportunityFactory}.cs`
- Modify: `src/AcxiomCrm.Infrastructure/Leads/LeadService.cs`; create `Infrastructure/Opportunities/NotAvailableOpportunityFactory.cs` (temporary, replaced in plan 06)
- Test: `tests/AcxiomCrm.Application.Tests/{LeadConversionTests,LeadConversionRollbackTests}.cs`

**Interfaces:**
- Produces:
```csharp
public sealed record ConvertOpportunityInput(string Name, decimal Amount, byte Probability, DateOnly ExpectedCloseDate, string? Notes);
public sealed record ConvertLeadCommand(int? ExistingCustomerId, bool CreateOpportunity, ConvertOpportunityInput? Opportunity, byte[] RowVersion);
public sealed record ConvertLeadResult(int LeadId, int CustomerId, int? OpportunityId);
public interface IOpportunityFactory {   // implemented by plan 06 using OpportunityRules and the same DbContext/transaction
    Task<Result<int>> CreateForConversionAsync(int customerId, int leadId, string ownerId, ConvertOpportunityInput input, CancellationToken ct = default);
}
```
- Behaviour: requires `leads.convert` and the lead `Qualified` and in scope. If `ExistingCustomerId` is null the customer is built from the lead (**name = lead name, company = lead company**, email/phone copied). If the lead lacks email or phone, return validation errors on `Email`/`Phone`: `Add an email address and phone number to the lead before converting.` Run `ICustomerService.FindDuplicateAsync`; on a duplicate return `Conflict` with form error `A customer with this email already exists. Link to the existing customer instead.` (the message never contains the other record's id or name). To offer the "link existing" option, add `Task<int?> FindConvertibleDuplicateCustomerIdAsync(int leadId, CancellationToken ct = default)` on `ILeadService`, which returns a customer id **only if that customer is in the caller's scope**. If `ExistingCustomerId` is given it must be in scope and active. Everything runs inside `BeginTransactionAsync`: opportunity via `IOpportunityFactory`, lead `MarkConverted`, explicit audit `Converted` (module Leads, `NewValue` JSON `{customerId, opportunityId}`), commit. Any failure rolls back and returns `Result.Fail`.
